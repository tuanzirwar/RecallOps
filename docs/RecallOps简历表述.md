# RecallOps 简历表述

## 推荐原则

RecallOps 的核心不是“做了一个混合 RAG”，而是解决研发故障记忆的完整生命周期：

```text
发现值得沉淀的故障 → 整理候选记忆 → 人工确认 → 版本化保存
→ 权限内检索 → 带证据回答 → 后续修订
```

简历必须区分已经实现的能力和设计中的能力。当前仓库已经实现 Tool Plugin、Draft、人工确认、权限、幂等、Revision、混合检索和离线评测；告警事件自动触发、延迟队列与 Curator Worker 尚未完整落地，因此不能直接作为已上线能力描述。

## 当前代码可证明版本

### RecallOps：基于飞书 OpenClaw 的研发故障记忆系统

**2025.04 – 2026.04** · **技术栈：** Python / FastAPI / TypeScript / OpenClaw / PostgreSQL / pgvector / RAG

面向故障结论散落在群聊、未经验证的信息容易污染知识库以及同类问题重复排查的场景，构建从候选整理、人工确认到证据检索和历史修订的团队故障记忆闭环。

- 基于 **OpenClaw Tool Plugin** 接入飞书话题，将多人故障讨论作为共享 Session，由 Agent 完成历史查询和候选故障整理；运行时注入可信用户身份，后端统一执行 Workspace 与角色权限校验。
- 设计 **Human-gated Memory**，将模型整理结果先保存为 Draft，经负责人修改和确认后再事务化写入正式记录；结合内容哈希、请求幂等、行锁与 Revision，处理重复整理、并发确认和结论变更。
- 构建 **FTS + pgvector + RRF** 检索链路，兼顾错误码、服务名等精确线索和自然语言症状；权限过滤前置到召回阶段，回答仅使用已确认记录并返回原始消息证据，证据不足时拒绝给出确定结论。
- 建立包含 identifier、paraphrase 和 no-answer 的离线评测集；在 1,140 条查询上取得 **HitRate@5 96.15%、Recall@5 89.02%、MRR 88.87%、无答案误召回率 5.0%**，本机检索 **P95 约 21 ms**，并通过失败样本分析识别语义基线和阈值策略的改进方向。

## 完成自动触发后使用的增强版本

以下版本只有在补齐 Trigger、Job Queue、Session State 和 Curator Worker 后才能写入简历。

### RecallOps：面向研发故障的自动记忆整理与混合检索系统

**2025.04 – 2026.04** · **技术栈：** Python / FastAPI / TypeScript / OpenClaw / PostgreSQL / pgvector / RAG

面向故障经验分散、复盘依赖人工整理以及同类问题重复排查的场景，构建“自动发现—候选整理—人工审批—可信检索—持续修订”的故障记忆生命周期。

- 设计事件驱动的 **Curator Agent**，由告警恢复、工单关闭和话题静默触发整理任务，通过延迟防抖和任务幂等避免反复扫描群聊；不同话题并行处理，同一话题通过状态锁串行化。
- 将 Agent 输出保存为带原始证据的 Draft，经负责人修改、通过或驳回后再写入正式记忆；通过一个话题一个活跃 Draft、内容哈希、请求幂等和 Revision 解决重复整理、并发审批与事实演进。
- 构建权限前置的 **FTS + pgvector + RRF** 混合检索，兼顾精确标识符和自然语言症状；回答严格绑定已确认记录及来源，对历史事实、当前现象、推测和待验证项分层表达。
- 建立有答案、改写和无答案查询组成的离线评测体系，以 **HitRate@5、Recall@5、MRR、误召回率和检索 P95** 衡量可用性，并结合失败分类持续优化召回、阈值和拒答策略。

## 面试开场

### 30 秒版本

> RecallOps 是一个研发故障记忆系统，不是把群聊直接写入向量库。系统以飞书故障话题作为短期 Session，由 Agent 整理候选故障，负责人确认后才转化为团队共享的正式记忆；查询时在权限范围内结合精确和语义检索，返回历史根因、处理方案和原始证据。项目重点是解决 Agent Memory 的触发、准入、并发、权限、版本和评测问题。

### 自动触发完成后的版本

> RecallOps 通过告警恢复、工单关闭和话题静默自动触发 Curator Agent，将一次故障讨论整理成带证据的 Draft，经负责人审批后沉淀为正式记忆。系统没有让 Agent 自主确认事实，而是把自动化放在整理阶段，把权限、审批、事务和版本留给确定性后端；后续通过混合检索和证据约束帮助研发快速复用历史经验。

## 指标口径

- `HitRate@5 96.15%`：Top-5 中至少出现一个相关故障的查询比例。
- `Recall@5 89.02%`：每条查询的相关故障被 Top-5 找回的平均比例。
- `MRR 88.87%`：第一个相关结果排名倒数的平均值。
- `无答案误召回率 5.0%`：180 条无答案查询中，仍返回可信结果的比例。
- `P95 约 21 ms`：只统计本机检索函数，不包含飞书网络、在线 Embedding 和 LLM 生成。

不能把 `96.15%` 写成 Recall@5，也不能把本机检索 P95 描述成端到端 RAG 延迟。

## 不建议使用的表述

- “Agent 自动判断根因并写入知识库”：正式事实仍需要审批。
- “每个用户拥有独立故障记忆”：记忆属于 Workspace，Session 属于故障话题。
- “混合检索显著优于全文检索”：当前离线基准中 FTS 更高，混合方案的价值是统一覆盖两类查询。
- “支持百万级数据”：当前评测验证的是策略和正确性，没有完成对应容量压测。
- “自动监听飞书并沉淀所有故障”：当前仓库尚未实现完整自动触发链路。
